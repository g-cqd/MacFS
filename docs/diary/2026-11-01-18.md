# Diary — 2026-11-01 (18)

## The first writable FSKit mount (roadmap 0046), and FSKit's two traps

| Claim | Probe | Verdict |
|---|---|---|
| FSKit asks for the mount options before activation | a log line in the getter | **REFUTED**: after; the volume now asks for read-write only once its writer began |
| The write handler carries every write | `dd` of 4 KiB to 4 MiB on a mounted copy, the module logging each call | **REFUTED**: 252 KiB arrives; 256 KiB (262144 bytes) never reaches the module, and the writer stays in the kernel (`U`) for good; `ioSize` 128 KiB changed nothing. Seven such processes remain until a restart, and hold the image they wrote to |
| Kernel-offloaded writes work | `blockmapFile` with the write flag answered by `mapForWriting`, `completeIO` by `completeWrite` | Holds, after the next row: every size, a 3 MB copy byte for byte |
| `completeIO`'s status can be read | three ways (cast, its bits inline, its bits out of line) | **REFUTED** in the Release module, each crashed it (`swift_getErrorValue` on null): the header declares non-null what the documentation says is nil on success. Fine in a standalone reproduction, even with whole-module optimization. Not read at all now |
| A range mapped for writing is all the reader's runs say | the first mapped-write test | **REFUTED**: the reader's runs stop at the size, so blocks linked past it were missing, and a second mapping would have allocated them again. A writer's runs go through the range |
| A completed write's size never covers unwritten data | every crash state | **REFUTED** until `completeWrite` flushes before the size |
| The probes' mounts were ours | the second image mounted | **REFUTED** twice: a copy with the stuck image's UUID was refused ("a file with the same name already exists"), and `dd` wrote into the APFS folder beneath; then GNU `dd` refused `bs=1m`. Copies now get their own UUID, and each step checks the mount first |

Live, on a copy of the ext2 image with its own UUID, mounted with `mount -F -t ext4`: writes of 4 KiB, 256 KiB, 1 and 4 MiB,
`cp` of the 3 MB random file and `cmp`, create and append, mkdir, mv (also a directory into another parent), `ln -s`, `ln`,
`rm`, `truncate`, `chmod`, `umount`. Then `e2fsck -fn` exit 0, and in the container `debugfs` dumps the 4 MiB file identical to
the copy taken through the mount, the moved file's text, the symlink, the hard link's two links and the 0600 mode. The checker
image gains `e2fsprogs-extra` (debugfs), tagged 2.

The mount check after: 35 of 36; ext2's FSKit mount is refused only because the stuck image holds its UUID until a restart.

Library: `WritableFileSystem.beginWriting` (one reader upgraded at activation, one cache), `Timestamp.now`,
`WritableBlockMapping` (`mapForWriting`, `completeWrite`); 3 mapped-write tests including every crash state. Mutation testing
